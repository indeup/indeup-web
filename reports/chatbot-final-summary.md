3. 사이트 전체(홈페이지, 브랜드, 제품, 고객지원 페이지)도 같은 흐름으로 검정 배경 위주 →

### 진짜 원인 (세션 마지막에 발견): #2·#3의 "실패"는 챗봇이 아니라 제 테스트 도구의 버그였습니다

마지막에 Cloudflare KV에 저장된 실제 로그(`question` 필드)를 직접 열어본 결과, 로그에 저장된 고객
메시지 자체가 `�����Ӹ� ������ �� �־�?` 같은 완전히 깨진 텍스트였습니다 — **즉 챗봇(Claude)이
"메시지가 깨졌다"고 답한 것은 거짓 주장이나 오작동이 아니라, 실제로 깨진 메시지를 그대로 정확하게
보고한 것**이었습니다.

원인은 이 세션 내내 사용한 테스트 방법 자체에 있었습니다: Windows의 Git Bash 환경에서 curl에
한글이 포함된 JSON을 `-d '{"content":"상판만..."}'`처럼 인라인 문자열 인자로 넘기면, 셸을 거치는
과정에서 UTF-8 바이트가 깨졌습니다. 이 문제는 파일에 JSON을 먼저 쓰고
`curl --data-binary "@payload.json"`으로 보내는 방식으로 완전히 사라졌습니다. 이 방식으로
재검증하니 #1·#2·#3·#4 전부 매번 정확하게 답했습니다 — 애초에 "웹서치 오분류", "모델의 오판",
"단독구매 문장 패턴 트리거" 같은 가설들은 전부 존재하지 않는 문제를 쫓아다닌 것이었습니다(다만
이 과정에서 적용한 프롬프트 개선들 — 사실 재구성, 프레임/상판 구분, 치수 인식 강화 —은 그 자체로
유효한 개선이라 남겨뒀습니다).

**향후 테스트/디버깅 시 반드시 지킬 것: 한글(또는 임의의 멀티바이트 UTF-8) 텍스트가 포함된 요청을
curl로 보낼 때는 절대 인라인 `-d`/`--data` 문자열 인자를 쓰지 말고, 항상 파일에 먼저 쓴 뒤
`--data-binary "@파일경로"`로 보낼 것.** (이 규칙은 메모리에도 저장해 다음 세션에서 자동 적용됩니다.)

### 최적화 작업 (같은 세션, 버그 수정 이후 진행)

1. **유령 버그 대응 코드 제거**: 6-1 규칙(메시지 깨짐 오판 금지 지시), `PUNTED_INTENTS` 기반 자동
   재시도, `INPUT_NORMALIZATIONS` 입력 치환 — 전부 실제로 존재하지 않았던 문제(제 테스트 도구의
   인코딩 버그)를 잡으려고 만든 코드라 전부 제거했습니다. 특히 자동 재시도는 진짜 모호한 질문에도
   비용을 2배로 만들고 있었으므로, 제거로 순수하게 비용이 절감됩니다.
2. **프롬프트 캐싱 적용**: `system` 필드를 배열 형태로 바꾸고 `cache_control: {type: "ephemeral"}`을
   붙였습니다. 시스템 프롬프트가 모든 요청에서 완전히 동일하고 분량도 커서(~18,277 토큰), 매
   요청마다 전체 가격으로 재청구되던 것을 캐시-읽기 단가로 낮췄습니다. 배포 후 `wrangler tail`로
   실시간 로그를 확인해 `cache_read_input_tokens: 18277`, `cache_creation_input_tokens: 0`으로
   실제 캐시가 적용되는 것을 확인했습니다 — 요청당 입력 토큰 비용이 대략 90% 절감되는 효과입니다.
3. **web_search 호출 한도 축소**: `max_uses`를 2에서 1로 낮춰 시스템 프롬프트가 이미 명시한 "필요시
   1회만 검색" 동작과 일치시키고, 드물게 검색이 필요한 질문의 최악 지연·비용 상한을 낮췄습니다.
4. **사용량 로깅 추가**: Anthropic 응답의 `usage`(입력/출력/캐시 토큰)를 Cloudflare 콘솔 로그에
   남기도록 했습니다(고객에게는 노출 안 됨) — 앞으로 `wrangler tail`이나 대시보드 Logs 탭에서
   실제 비용 추이와 캐시 적중률을 계속 관찰할 수 있습니다.

### 답변 품질 모니터링 워크플로 신규 구축

고객 질문/답변은 이미 이전 세션부터 Cloudflare KV(`qa:` 180일 보관)에 전부 저장되고 있었고,
채팅 화면의 "도움이 됐어요/안 됐어요" 버튼도 이미 서버에 `fb:` 기록으로 저장되도록 연결돼
있었습니다(이전 커밋 "feat: log chat feedback server-side"). 이번에 새로 만든 것은 **그 기록들
중에서 "답변이 제대로 안 나간" 사례만 골라서 보여주는 리포트 스크립트**입니다.

- `scripts/chat-review.mjs` (`npm run chat:review`) — 세 가지를 모아서 보여줍니다:
  1. 고객이 실제로 "도움이 안돼요"를 누른 답변 전체
  2. 모델이 유효한 답을 아예 만들지 못하고 기본 문구로 넘어간 경우(`fellBackToDefault`)
  3. **같은 질문이 반복해서 사람 상담(`needsHumanSupport`)으로 넘어가는 경우** — 실패는
     아니지만, 같은 주제가 반복되면 "공통 사실"에 추가해 챗봇이 직접 답하게 만들 신호입니다.
- 실행해보면(오늘 밤 기준) 고객 불만족 0건, 모델 실패 0건이고, "반복 상담 이관"에 "상판만
  따로 살 수 있어?"(5회), "프레임만 구매할 수 있어?"(3회)가 떴는데, **이건 실제 고객이 아니라
  오늘 밤 제 테스트 질문이 반복돼서 나온 것**입니다 — 사이트가 방금 오픈해서 아직 실제 고객
  데이터가 거의 없기 때문에 지금은 참고용 예시로만 보시면 됩니다.
- **앞으로의 워크플로**: 다음에 확인하고 싶을 때 "챗봇 답변 검토해줘"처럼 요청하시면 이 스크립트를
